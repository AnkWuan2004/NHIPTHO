# C-010 — ESP32 DevKit DHT22 local alarm vertical slice

status: done
deps: C-005, C-009

risk-reason: A new device-token endpoint accepts sensor writes and drives a physical alarm; incorrect freshness, threshold, or fail-safe behavior could create silent or repeated warnings.
risk-ack: none

## Scope

Add one ESP32 DevKit V1 firmware path using DHT22, buzzer, and red LED. The firmware samples temperature/humidity every 2 seconds and posts to `/api/environment/readings` with a device token. The backend persists the reading, combines the temperature with the latest BPM result that is no more than 120 seconds old, and returns the contract-defined `AlarmDecision` including the current temperature threshold. A temperature-only alarm is `warning`; any fresh breathing reason is `critical`; normal is `none`. The firmware turns the buzzer and LED on for a combined active decision; if the backend is unavailable, it retains the last known/default 30°C temperature threshold locally and disables only the breathing-alert portion. Temperature handling must not invent a breathing alarm. Extend the caregiver dashboard with the latest environment reading and alarm reason, and document wiring, configuration, fixture fallback, and hardware limitations.

## Independent test

The operator can send a DHT22-shaped reading to the local API and see a persisted temperature/humidity record plus an alarm decision: high temperature activates `temperature_high`, a recent out-of-range BPM activates the matching breathing reason, and normal or stale-BPM input deactivates the breathing alarm. With the physical ESP32 available, the same responses switch the buzzer and red LED on/off.
